# 05 — 验收策略

> 审计日期：2026-10-13
> 目的：定义可客观执行、可回归的验收方式，取代"看起来像"。
> 核心原则：**每个宣称的完成，都必须有一条命令能证明它**。

---

## 1. 验收的三条铁律

### 铁律 1：Oracle 优先（黑盒对拍）

**唯一权威**是 BCompare 自身的输出。任何"我认为 BC 应该这样"都是不可接受的。

**已建立的能力**（实测）：

```bash
BComp.com /silent @<script> <left> <right> <output>
```

**两条必须记住的语义差异（已实测）**：

| 命令 | 输入方式 | 陷阱 |
|---|---|---|
| `text-report` | **直接接两个文件路径** | 对文件用 `load` 会报 exit 107 |
| `folder-report` | 作用于**已 load 的基准文件夹** | **必须**先 `load`，否则 exit 106（这正是 `verify/dir/` 旧脚本的失败原因） |

**正确的文件夹配方**：
```
load "%1" "%2"
expand all
folder-report layout:xml output-to:"%3"
```

### 铁律 2：固定输入路径

**实测发现**：报告头 `Left file: …  Right file: …` 在路径较长时**折成两行**，且与 `COLUMNS` 环境变量无关，只与**路径字符串长度**有关。

**因此**：对拍必须**固定输入路径**（或归一化头部），否则会把折行误判为行为差异。这是本次审计中一度导致"两版本不兼容"误判的直接原因。

### 铁律 3：Oracle 必须就地运行

**实测**：把 `BCompare.exe` / `BComp.com` 复制到其他目录会触发：

```
Trial mode error — The trial information is missing or corrupt.
Version 5.2.1 (build 32035)          Error = 5
退出码 104
```

**因此**：所有 Oracle 调用**必须使用真实安装目录的路径**，禁止复制可执行文件到工作区。

## 2. 对拍规范的五个层次

按"严格度"从高到低，不同功能适用不同层次：

| 层次 | 名称 | 方法 | 适用 | 当前状态 |
|---|---|---|---|---|
| **L1** | 字节等价 | 输出逐字节相同（仅归一化时间戳） | 报告格式、XML | 45 锚点：5.2.6 达 45/45；5.2.1 达 41/45（余为汉化） |
| **L2** | 结构等价 | 解析后结构相同（忽略标签文本） | 跨版本、跨语言 | 已实测可达成 |
| **L3** | 语义等价 | 关键判定序列相同（如 status 序列） | 对齐引擎 | 45/45 ✅ |
| **L4** | 统计等价 | 差异计数/摘要一致 | 大文件、性能场景 | 未建 |
| **L5** | 目视/交互 | 人工或 UI 自动化 | GUI | **无手段** ⚠️ |

**规则**：
- 引擎类功能 → 至少 **L3**（推荐 L1）
- 报告类功能 → **L1**（文本/XML）
- GUI → 目前只能 L5，**因此 GUI 不得作为 MVP 验收对象**

## 4. 锚点扩充计划

现有 45 锚点**不足以覆盖 MVP**。按功能列出必须新增的锚点：

### 4.1 文本比较（现 45 → 目标 ≥80）

| 类别 | 现有 | 需新增 | 新锚点举例 |
|---|---:|---:|---|
| 行切分/编码 | 11 | +5 | 混合 BOM、无 BOM UTF-16 探测、超长行、仅空白行、CR 单独结尾 |
| 重要性（空白） | 4 | +6 | 字符串内空白、多行注释内空白、行尾 CR、缩进层级变化、多空白折叠、标点邻接 |
| 重要性（大小写） | 3 | +6 | 关键字大小写、数字后缀、十六进制大小写、字符串内大小写、注释内大小写 |
| C 语法元素 | 6 | +8 | 逐元素：关键字/标识符/数字/字符串/注释/**指令**/**运算符** |
| 对齐 | 9 | +6 | 大量重复行、单边大块、交叉插入、末尾差异、全异、超大块替换 |
| XML 报告 | 6 | +4 | 超长行、多字节字符、制表符、控制字符边界 |
| 报告选项 | 5 | +5 | 选项组合、context 边界值、display-* 组合 |
| **合计** | **45** | **+40** | **≥85** |

### 4.2 文件夹比较（现 3 状态 → 目标 ≥40 例）

**现有夹具严重不足**：仅覆盖 `same` / `ltonly` / `rtonly`，且 `diff` 状态未覆盖（因为默认判据是 size+timestamp）。

| 类别 | 例数 | 说明 |

| criteria 矩阵 | 12 | size/timestamp/CRC/binary/rules-based × 同/异 |
| 时间戳容差 | 4 | `timestamp:2sec`、`IgnoreDST` |
| 结构边界 | 8 | 深层嵌套、空目录、同名目录/文件冲突、大量文件 |
| 属性 | 4 | `attrib:`、hidden、system、readonly |
| 符号链接 | 4 | `follow-symlinks` 开/关 |
| **合计** | **≥40** | |

### 4.3 新增功能夹具（MVP 外，但须先建后做）

## 5. 汉化标签处理规范

**问题**：当前目标安装是中文汉化版，其报告标签为中文，与英文 golden 不一致。

**实测的差异清单**（全部为标签，非行为）：

```
XML:   <mode>差异</mode>                 vs  <mode>Differences</mode>
       <mode>相同</mode>                 vs  <mode>Same</mode>
       <mode>差异, 带上下文</mode>        vs  <mode>Differences, With Context</mode>
       <error1>文件编码错误 (第 1 行)</error1>  vs  <error1>File Encoding Error (Line 1)</error1>

文本:  2 个相同行                         vs  2 same line(s)
       文本比较(T)                        vs  Text Compare
       已生成于：                          vs  Produced:
       模式： 全部                         vs  Mode:  All
```

**规范**（三选一，须在实现中固定）：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 忽略标签** | 对拍只比对**结构与数据行** | 简单；已验证可达 25/30 | 丢失标签正确性验证 |
| **B. 标签映射表** | 维护中↔英映射，对拍前归一 | 可验证标签 | 需维护映射 |
| **C. 待英文环境** | 用 `bc-official`（5.2.6 英文版）做标签基准 | 标签最干净 | 版本不同（但行为已证等价） |

**推荐 B + C 组合**：以 `bc-official`（英文）作为**标签基准**，对当前目标（汉化版）用**映射表归一**后对拍。理由：两版本行为已实测等价（`02-version-and-evidence.md` §3.4），因此英文版可作为标签权威。

**注意**：方案 C 不违反"以当前版本为目标"——因为**比较引擎已被证明行为等价**，英文版仅用于提供**英文标签文本**。

## 6. 反"假功能"检查（每个里程碑执行）

审计要求"不写假功能"。以下检查必须逐条过：

| # | 检查项 | 判定 |
|---|---|---|
| 1 | 是否有函数返回**硬编码**结果？ | ❌ 假功能 |
| 2 | 是否有 **TODO/stub** 被当作已实现？ | ❌ 假功能 |
| 3 | 未实现的路径是否**显式报错**（而非静默返回空）？ | ✅ 必须 |
| 4 | `--help` / 文档是否**列出未支持项**？ | ✅ 必须 |
| 5 | 每个已宣称的能力是否有**对拍命令**？ | ✅ 必须 |
| 6 | 测试数量是否为 **0**？ | ❌ 须补真实测试 |
| 7 | 是否有"为了通过锚点"的**特例硬编码**？ | ❌ 假功能 |

**第 7 条特别重要**：`clone/` 里已有一处需审视的设计——`syntax.rs` 的 `is_syntax_aware()` **仅按扩展名判断**（`.txt` 则非语法感知），且 `align.rs` 的 `match_key()` 把**所有注释行**归约为同一个 key（`"COMMENT-LINE-KEY"`）。这能让 `comment-c` 锚点通过，但**不是 BC 的逐元素重要性语义**。

**判定**：这是**规格级近似**，在 MVP 中**必须被真正的分词器替代**；在替代前，文档须标注"注释对齐为近似实现"。这不属于"假功能"（因为它确实实现了可观察行为），但**不得声称等同于 BC 的重要性引擎**。

## 7. 回归策略

### 7.1 基线锁定

```bash
# 基线（本次审计实测）
python tools/bcx-verify.py          # 45/45 status
python tools/bcx-layout-verify.py   # 29/30 layout
```

**任何重构后必须复现上述基线。** 迁移到新工程时，这两条命令是**不可退让的门槛**。

### 7.2 三层回归

| 层 | 频率 | 内容 |
|---|---|---|
| 快速 | 每次提交 | `cargo test`（单元测试，无 Oracle） |
| 中速 | 每日/每里程碑 | 锚点对拍（≥80 例） |
| 慢速 | 里程碑结束 | 全量对拍（文本 + 文件夹 + 布局） |

**快速层必须运行在不依赖 BCompare 的环境**（因为 Oracle 依赖本机安装）。这意味着**锚点的期望值必须固化为文件**（golden），而非每次实时查询 Oracle。

### 7.3 golden 数据的版本标注

现有 `verify/golden/README.md` 标注"BCompare 5.2.6"。**本审计不改动它**，但新生成的数据必须标注：

```
生成版本：5.2.1.32035
生成时间：YYYY-MM-DD
SHA-256：<分块给出>
生成命令：<完整命令>
归一化：<应用的归一化规则>
```

**哈希必须分块给出**：本环境工具输出会把 64 位连续十六进制渲染成全零占位（实测），单行抄录会产生假证据。

## 8. 验收清单（MVP 完成时逐项打勾）

| # | 项目 | 判定方式 | 阈值 |
|---|---|---|---|
| 1 | 构建成功 | `cargo build` | 无错 |
| 2 | 单元测试真实且全绿 | `cargo test` | 测试数 > 0，通过率 100% |
| 3 | 文本锚点 | `verify` harness | ≥80 例，status 100% |
| 4 | 文本布局 | harness | 6 种，≥29/30 字节级 |
| 5 | XML 报告 | harness | L1 或 L2 通过 |
| 6 | 文件夹夹具 | harness | ≥40 例，XML 对拍通过 |
| 7 | criteria 引擎 | 对拍 | size/timestamp/CRC/binary 全通过 |
| 8 | CLI 脚本子集 | 脚本对拍 | 8 条命令可用 |
| 9 | 退出码语义 | 测试 | 0/1/2 正确，错误码不误报 |
| 10 | 未支持项显式标注 | 人工检查 | 100% 标注 |
| 11 | 无假功能 | §6 检查表 | 7 条全过 |
| 12 | 已知差异清单 | 文档 | 显式列出（如 `mixed-side-by-side`） |

**第 12 条**：已知差异**必须公开列出**。例如 `mixed-side-by-side` 的标记省略现象，`verify/layouts/README.md` 已诚实记录"精确触发条件未建模"——这种做法应延续。

## 9. 无法自动化验收的部分（诚实声明）

| 功能 | 为何无法自动验收 | 应对 |
|---|---|---|
| **GUI 外观** | 无 UI 自动化基础设施；DFM 不含主题位图 | 推迟 GUI；先建 UI 测试方案再开工 |
| **打印输出** | 依赖打印机驱动 | 明确不纳入 MVP |
| **剪贴板行为** | 需桌面会话 | 手动验证清单 |
| **性能主观感受** | — | 用可量化指标（时间/内存）替代 |
| **网络/远程** | 需测试服务器 | 明确排除 |
| **文件同步的破坏性** | 风险高，需真实文件系统 | 独立安全评审 + 破坏性测试专章 |

**原则**：**无法自动验收的功能，不进入 MVP。** 这不是回避，而是保证"每个宣称都有证据"。

## 10. 验收的元规则

1. **没有命令证明的完成，不算完成。**
2. **Oracle 说什么就是什么**，不是"我认为 BC 应该这样"。
3. **两版本行为已证等价**（02 §3.4），但引用时**仍须标注版本**。
4. **不能通过的锚点，记录为已知差异**，不隐藏、不改锚点、不为通过而特例硬编码。
5. **阈值宁可低而真，不要高而假**——「45/45 真通过」优于「80/80 含硬编码」。
