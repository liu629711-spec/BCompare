# 03 — 架构方案

> 审计日期：2026-10-13
> 目的：为 GUI、核心算法、文件系统、远程资源、脚本系统给出**至少两种**可选架构，并给出推荐与理由。
> 约束前提（来自 00/01/02 的实测结论）：已有 661 行 Rust 规格验证器；已有 Oracle 工具链；目标平台 Windows 优先。

---

## 0. 架构必须解决的四个硬约束

这四个约束来自实测证据，不是偏好：

### 约束 A：所有内容类型共享同一套对齐框架

**证据**：BC 的 9 种引擎命名为 `TextMap` / `TableMap` / `PixMap` / `HexMap` / `RegMap` / `MediaMap` / `VerMap`（`report-algorithm.md`，**I** 级但命名高度一致）；官方提供 9 个对应报告命令（`text-report`/`table-report`/`hex-report`/`picture-report`/`media-report`/`registry-report`/`version-report`/`folder-report`/`data-report`，**O** 级）。

**含义**：不能写成 9 个独立工具。必须有 **`CompareEngine` 抽象 + 通用对齐框架**。

### 约束 B：文件系统必须抽象（本地/压缩包/远程统一）

**证据**：BC 有 `Source\Vfs\` **17 个单元**（`VfsFtpResourceImpl.pas`、`VfsWebDAVResourceImpl.pas`、`VfsOneDriveResourceImpl.pas`…，**D** 级）；压缩包可当目录比较（`archive_files.html`，**O** 级）。

**含义**：文件夹比较必须建立在 **VFS 接口**之上，而不是直接调用 `std::fs`。否则后期加压缩包/远程要重写。

### 约束 C：GUI 是数据驱动的（211 个窗体是结构化数据）

**证据**：`extracted/ui-spec.json` — **211/211 表单完全解析，0 失败**（**O** 级）；每个窗体含控件树、几何、对齐、事件绑定、Tab 顺序。

**含义**：GUI 不必手写 211 个窗体。可设计**声明式窗体描述 → 运行时生成**。这是本项目最大的降本机会。

### 约束 D：可验证性优先

**证据**：本项目已建成 Oracle 工具链（45 锚点 status 对拍、30 布局对拍、文件夹报告对拍），且实测**两版本行为等价**（02 §3.4）。

**含义**：架构必须让**每个引擎都能独立对拍**。这要求引擎是**纯函数式核心 + 薄 IO 层**（便于夹具注入）。

## 1. 核心算法架构

### 方案 1A：分层核心（推荐）

```
┌─────────────────────────────────────────────────────┐
│  Application / CLI / GUI                            │
├─────────────────────────────────────────────────────┤
│  Session layer    会话模型、规则配置、持久化          │
├─────────────────────────────────────────────────────┤
│  Engine layer     每类内容一个 engine：               │
│                   TextEngine / DirEngine / HexEngine │
│                   TableEngine / PixEngine / …        │
│   每个 engine 实现：                                  │
│     - tokenize / load   →  内容模型                   │
│     - compare           →  DiffMap                    │
│     - report            →  布局渲染                   │
├─────────────────────────────────────────────────────┤
│  Alignment layer  ★ 共享 ★                            │
│     Myers(线性空间) + 前后缀裁剪 + 段合并 + 可取消     │
│     输入：两个序列（行/记录/字节块）                   │
│     输出：EditScript（匹配对 + 差异段）                │
├─────────────────────────────────────────────────────┤
│  Importance layer ★ 共享 ★                            │
│     逐元素重要性：CaseSig / Weights / 强制重要         │
│     三态：same / similar / different                  │
├─────────────────────────────────────────────────────┤
│  VFS layer        ★ 共享 ★                            │
│     本地 / 压缩包 / 远程 —— 统一 FileSystem 接口       │
├─────────────────────────────────────────────────────┤
│  Report layer     布局渲染（文本 / XML / HTML）        │
└─────────────────────────────────────────────────────┘
```

**优点**
- 直接对应约束 A/B/C/D。
- 对齐层与重要性层是**已验证**的部分（clone 45/45），可**原样迁移**并保持回归绿。
- 每个 engine 独立可测：给定夹具 → 断言 DiffMap，无需 GUI/网络。
- 与 BC 的 `*Map` 模式同构，行为兼容性更容易达成。

**缺点**
- 需要先定义好 `CompareEngine` trait，早期抽象成本。
- 序列抽象若过度泛化，可能拖慢文本路径（需保证零成本抽象）。

**关键设计决策**

| 决策 | 选择 | 理由 |
|---|---|---|
| 对齐输入类型 | 泛型序列 `&[T] where T: Eq`，或**哈希化整数序列** | `report-algorithm.md` 显示 BC 也是先做行→哈希归约（**I**）。哈希化可让所有引擎共用同一 Myers 实现 |
| 重要性位置 | **对齐后**（后处理），非对齐中 | BC 的 `FUN_140de5840` 维护"不重要行索引数组"，是独立层（**O** 结构） |
| 段合并 | 对齐输出时合并相邻差异 | BC `FUN_140dc6a00/b20` 的游程合并（**O**）；也是 UI"差异段"的数据来源 |
| 取消机制 | 每轮 D 迭代回调一次 | BC 同构（**O**） |

### 方案 1B：单引擎 + 插件（备选）

单一 `DiffEngine`，内容类型通过**插件**注入 tokenizer 与 renderer。

**优点**：实现更少；早期更快。
**缺点**：文件夹比较**不是**序列对齐（是树/集合比较），硬塞进序列模型会变形；表格比较的行匹配也非标准 LCS。**与约束 A 冲突**。

**结论**：**不推荐**。文件夹与表格的语义差异过大。

### 方案 1C：每引擎独立（不推荐）

每个内容类型一个完全独立的实现。

**缺点**：直接违反约束 A；9 套重复的对齐/重要性/报告代码；无法共享验收资产。**明确不采用**。

## 2. 文件系统 / VFS 架构

### 方案 2A：`FileSystem` trait + 多实现（推荐）

```rust
pub trait FileSystem {
    type Entry;
    fn read_dir(&self, path: &Path) -> Result<Vec<Self::Entry>>;
    fn metadata(&self, path: &Path) -> Result<Metadata>;
    fn open_read(&self, path: &Path) -> Result<Box<dyn Read>>;
    // 写操作单独 trait（避免只读实现被迫实现写）
}

pub trait WritableFileSystem: FileSystem {
    fn open_write(&self, path: &Path) -> Result<Box<dyn Write>>;
    fn remove(&self, path: &Path) -> Result<()>;
    // 同步/复制功能才需要
}
```

实现：`LocalFs`、`ArchiveFs`（zip/7z/tar）、`RemoteFs`（FTP/SFTP/WebDAV/S3）。

**优点**
- 文件夹比较**只依赖 `FileSystem`**，因此压缩包/远程比较**自动获得**。
- **只读/可写分离**：比较功能只需只读；破坏性的同步功能才需可写——这是**安全性设计**，与功能 4 的高风险对应。
- 远程实现可独立开发/测试，不阻塞主路径。

**缺点**：`Path` 语义在远程场景下需自定义（BC 用 `ltpath`/`rtpath` 字符串，见文件夹报告 XML）。

**关键决策**：**路径统一用字符串而非 `std::path::Path`**。
理由：实测的文件夹报告 XML 使用 `<ltpath>D:\Rea\verify\dir\trees\L</ltpath>` 这样的**不透明字符串**；远程路径（`ftp://host/path`）无法表示为本地 `Path`。早期就用字符串可避免后期重构。

### 方案 2B：挂载式（先映射到本地盘符）

远程资源先挂载为本地路径，复用 `std::fs`。

**优点**：实现最省。
**缺点**：依赖系统挂载能力；压缩包无法挂载为盘符；凭据管理受系统约束；**无法覆盖功能 9（压缩包）**。

**结论**：**不推荐**。

## 3. GUI 架构

### 方案 3A：数据驱动 + 原生 Rust（推荐，若选 Rust）

利用 211 个已解析的 DFM 作为**行为规格**，自研声明式 UI 描述：

```
DFM (提取物, 只读参考)  →  自研 UI 描述格式  →  运行时生成控件
                            (不复制 BC 位图/文本)
```

技术选项：`egui` / `iced` / `slint` / 原生 Win32 + `windows-rs`。

**优点**
- 211 窗体的**布局/对齐/事件绑定**可直接复用为规格，工作量从"手写 211 窗体"降到"实现渲染器 + 描述加载"。
- 跨平台潜力。

**缺点**
- 与 BC 的**像素级一致**不可能（DFM 不含主题位图；主题由 VCL 运行时合成）。
- 需自建 UI 测试手段（当前**无 GUI 自动化基础设施**）。

### 方案 3B：.NET + WPF/WinUI（推荐，若接受 .NET）

环境已有 **.NET 8.0.422**（实测）。

**优点**
- WPF 的布局系统（`Grid`/`DockPanel`/`DockPanel` 停靠）**天然对应** DFM 的 `Align`/`Anchors`/`Constraints` 模型——映射成本远低于自研布局引擎。
- 高 DPI、主题、无障碍**由框架提供**，直接覆盖功能 16 的大部分要求。
- 成熟的 UI 自动化测试（`FlaUI`/UIA）——**填补当前验收空白**。

**缺点**
- 与 Rust 核心的互操作需要 FFI（或核心也用 C#）。
- 分发体积较大。

### 方案 3C：Electron / Web 前端

**缺点**：与"Windows 桌面工具、高性能大文件比较"的目标冲突；体积大；本地集成弱。**不推荐**。

### GUI 决策建议

| 情形 | 推荐 |
|---|---|
| 核心用 Rust，接受较长 UI 工期 | **3A**（`egui` 起步，或 `slint` 求更原生观感） |
| 优先 GUI 完成度与可测试性 | **3B**（.NET WPF），核心可用 C# 或 Rust+FFI |
| 追求最小总工作量 | **3B**：WPF 的布局/DPI/主题/自动化测试都是现成的 |

**共同要求**：无论选哪种，**GUI 不得早于引擎**。理由：GUI 无法自动验收（01 §4），而引擎可以。先做引擎可保证每一步都有客观证据。

### GUI 选型定案（2026-10-20，用户批准 3B）

**Rust 核心 + .NET WPF 前端**。判据全部来自本项目实测纪律：
1. **验收体系的命脉是 UIA**——四份活体 Oracle 基线（docs/19）全靠 pywinauto UIA
   读取；WPF 是 UIA 第一公民（AutomationId/Name/控件类型/菜单模式原生），
   测产品与测 Oracle 用同一套 harness。egui/Slint 走 AccessKit 二等公民桥，
   刚在 BC 的 VCL 桥（ExpandCollapse 不实现）上吃过三轮试错的教训。
2. 复刻目标本身是原生 Win32 观感（VCL）：WPF 系统主题/原生弹出/高 DPI 天然接近。
3. **验收闭环已端到端验证**（P1-WPF-1~4，见 docs/19 §6）：descriptor→渲染→
   `--dump`→结构门禁 full 级 0 diff；UIA 自检（`tools/uia-selfcheck.py`）产品
   窗口活体树逐具名节点断言全绿。ADR-7 的同构 JSON 契约在 WPF 侧坐实。
   工程位置：`product/gui/WpfHost/`（net8.0-windows，本机 SDK 8.0.422 就绪）。
4. 代价（已接受）：.NET 运行时边界；FFI/进程边界调 Rust 引擎。

原"GUI 不得早于引擎"要求继续适用于**功能视图**（Text/Folder 比较视图等依赖
引擎数据）；对话框/壳类窗体不依赖引擎，可先行，且每一个都进门禁。

## 4. 远程资源架构

### 方案 4A：trait 抽象 + 开源协议库（推荐）

```
RemoteFs ──┬── FtpFs     (自研 RFC959 子集 或 开源库)
           ├── SftpFs    (ssh2 / russh)
           ├── WebDavFs  (HTTP + XML)
           └── S3Fs      (HTTP + SigV4)
```

**优点**：与 2A 的 `FileSystem` trait 自然衔接；可用成熟开源库。
**缺点**：TLS/SSH 依赖引入；凭据存储需独立设计（**安全敏感**）。

### 方案 4B：外部工具桥接（如调用 `rclone`/`curl`）

**优点**：几乎零协议实现工作。
**缺点**：外部依赖、性能差、错误处理粗糙、无法流式。

### 远程决策建议

**排除出 MVP 与首年范围**（01 §2 功能 10）。若必须做，用 **4A**，并**明确不复用 BC 的 SecureBlackbox 相关行为**。

**凭据安全要求**（独立于方案）：
- 不在日志/报告中回显密码；
- 用 OS 凭据存储（Windows Credential Manager）；
- 实测已确认 BC 的 `/silent` 报告路径**不写配置文件**（`verify/golden/README.md`，**O**）——这是好的安全语义，应效仿。

## 5. 脚本系统架构

### 方案 5A：解释器 + 命令对象（推荐）

```
脚本文本 → 词法/语法分析 → 命令列表 → 逐条执行 → 会话状态机
```

命令集来自官方文档（**O**）：`load` / `criteria` / `filter` / `expand` / `select` / `text-report` / `folder-report` / `copy` / `copyto` / `sync` / `snapshot` / `log` / `option` 等。

**关键语义（已实测）**：
- `load` **只接受文件夹**；对文件用 `load` 报 `Fatal Scripting Error`（exit 107）。
- `folder-report` 作用于**已 load 的基准文件夹**，因此必须 `load` 在前（**本次审计修复的真实缺陷**）。
- `text-report` 则**直接接受两个文件路径**。
- `/silent` 抑制交互；退出码有语义（`0` 成功 / `104` 授权 / `105`–`107` 脚本错误）。

**优点**
- 规格完备（官方文档 + 实测配方），可先实现最小子集立即支撑验收。
- 命令对象模式便于逐命令对拍。

**缺点**：DSL 命令众多（官方 9 个报告命令 + 20+ 操作命令），需按需实现。

### 方案 5B：内嵌通用脚本语言（Lua/Rhai/JS）

**优点**：表达力强；用户可编程。
**缺点**：**与 BC 脚本不兼容**——而兼容性是本项目的验收基础（Oracle 对拍依赖脚本）。**不推荐作为主接口**；可作为**补充**的扩展机制。

### 脚本决策建议

**采用 5A**，并按**兼容优先**实现命令子集：

```
阶段 1（MVP）：load / criteria / expand / filter / text-report / folder-report / log / option
阶段 2：select / copy / copyto / sync / snapshot
阶段 3：其余
```

## 6. 推荐总体架构（综合）

```
┌────────────────────────────────────────────────────────────┐
│  UI 层：数据驱动窗体（211 DFM 作规格）                       │
│  推荐 .NET WPF（布局/DPI/主题/自动化测试现成）                │
│  ← 最晚做，且必须有 UI 自动化测试才开工                        │
├────────────────────────────────────────────────────────────┤
│  接口层：CLI + 脚本解释器（兼容 BC 命令子集）                 │
│  ← MVP 需要（支撑验收）                                      │
├────────────────────────────────────────────────────────────┤
│  会话层：比较配置模型 + 持久化（BCSessions.xml 兼容）          │
├────────────────────────────────────────────────────────────┤
│  引擎层：Text / Dir / Hex / Table / Pix / Reg / Ver         │
│  每个 engine = load + compare + report                       │
│  ← MVP 只做 Text + Dir(只读)                                │
├────────────────────────────────────────────────────────────┤
│  ★ 共享：Alignment（Myers+裁剪+段合并+可取消）  ← 已验证      │
│  ★ 共享：Importance（CaseSig/Weights/强制重要）              │
│  ★ 共享：VFS（只读 FileSystem trait）                        │
│  ★ 共享：Report（文本/XML/HTML 渲染）                        │
└────────────────────────────────────────────────────────────┘
```

### 语言选型建议

| 选项 | 优点 | 缺点 | 适用 |
|---|---|---|---|
| **Rust 核心 + .NET WPF GUI** | 核心性能与安全性好；GUI 生态成熟 | FFI 边界成本 | **推荐**（若要 GUI） |
| **全 Rust** | 单一语言；`egui`/`slint` | GUI 生态与自动化测试弱于 WPF | 推荐（若可接受 UI 工期） |
| **全 .NET** | 开发效率高；工具链统一 | 大文件性能需谨慎 | 备选 |
| **C++** | 性能最好 | 开发效率低、内存安全风险 | 不推荐 |

**推荐路径**：**Rust 核心 + CLI 优先**；GUI 选型推迟到引擎稳定后再定（届时可评估 `egui` vs WPF）。

理由：MVP 的验收**完全依赖 CLI + 报告对拍**，不需要 GUI；而 clone 已有 661 行 Rust 资产可迁移。推迟 GUI 选型可避免过早绑定。

## 8. 与现有 `clone/` 资产的关系

**不修改 `clone/`**（遵守约束）。但建议**新工程复用其算法**：

| clone 资产 | 复用方式 |
|---|---|
| `lines.rs` 行切分/编码 | 迁入新工程 `text/parse.rs`，扩锚点后保留 |
| `align.rs` LCS DP | **替换为 Myers**（BC 实测用 Myers；DP 是 O(n·m) 内存，大文件不可用） |
| `syntax.rs` | **重写**（当前是启发式，非真正分词器） |
| `report.rs` + `layouts.rs` | 迁入 `report/` 并扩充 |

**关键升级点**：`align.rs` 用 LCS DP，内存 O(n·m)。BC 用 Myers 线性空间 O(n)。**大文件必须换成 Myers**——且 `report-algorithm.md` 的伪代码结构（**O**）已给出实现蓝图。

**迁移验收**：迁移后 `bcx-verify.py` 必须仍为 **45/45**，`bcx-layout-verify.py` ≥ **29/30**。这保证了重构不回归。
