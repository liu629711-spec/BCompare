# 04 — 里程碑与最小切入点

> 审计日期：2026-10-13
> 目标：给出一个 **2–4 周内可交付的可用 MVP**，同时保留向完整套件扩展的架构。
> 前提：不写假功能；不声称 1:1；每个阶段有客观验收。

---

## 0. MVP 的定义（先说清"不做什么"）

### MVP 交付物

一个 **Windows 命令行工具**（暂名 `reacmp`），具备：

1. **文本比较**：两个文件 → 与 BC 一致的 same/similar/different/orphan 判定
2. **文本报告**：输出 6 种布局（side-by-side / interleaved / patch / summary / statistics / over-under）+ XML
3. **文件夹比较（只读）**：两个目录 → 与 BC 一致的状态判定（含 criteria 模型）
4. **文件夹报告**：side-by-side / summary / xml
5. **CLI 兼容子集**：`load` / `criteria` / `expand` / `filter` / `text-report` / `folder-report` / `log` / `option` + `/silent` + 退出码语义
6. **重要性规则**：纯文本 + C/C++/Python/JS 四种格式的最小规则集

### MVP **明确不做**

| 不做 | 理由 |
|---|---|
| GUI | 无验收手段；工作量极大（01 §4） |
| 三方合并 | 规格缺口 U2 |
| 文件复制/同步 | **唯一破坏性模块**，须独立安全评审 |
| 表格/图片/二进制/注册表/版本 | 各自需独立夹具与探测 |
| 压缩包/远程 | 规格最薄；VFS 先留接口不实现 |
| 会话持久化 | 可与 CLI 解耦，后置 |

**判断依据**：MVP 的功能全部**已有黄金数据或完整规格**（01 §4），因此每一步都可客观验证。这是把 2–4 周变成"可交付"而非"又一轮探索"的关键。

## 1. 四周计划（含并行性）

### M0：验证基建归一（2–3 天）— 阻塞项，其余全部依赖它

| M0.1 建统一对拍框架 | `product/verify/` 下的 harness | 能批量跑锚点并输出通过率 |
| M0.2 固定 Oracle 配方 | Oracle 调用封装（**必须在真实安装目录执行**） | 调用成功且退出码 0 |

## 2. 并行性分析（供多代理派发）

| 里程碑 | 可并行？ | 说明 |
|---|---|---|
| M0 | ❌ **串行**（阻塞） | 必须最先完成，全项目依赖 |
| M1 | ⚠️ 部分 | M1.1/M1.2 与 M1.3/M1.4/M1.5 可两路并行；但都要改同一 crate，**不建议同批编辑同一组文件** |
| M2 | ⚠️ 部分 | M2.1（探测，写 `product/verify/`）与 M2.2（分词器，写 `core/`）**文件不重叠**，可并行 |
| M3 | ✅ **可独立并行** | M3 只依赖 M0；与 M1/M2 **文件不重叠**（独立 crate `dir/`），可全程并行 |
| M4 | ❌ 依赖 M1+M2+M3 | CLI 需先有引擎可调 |

**推荐并行方案**：
- **批次 A**：M1（文本核心）+ M3（文件夹比较）——两者文件不重叠，可并行
- **批次 B**：M2（重要性）——依赖 M1 的对齐层
- **批次 C**：M4（CLI）——依赖全部

## 3. 2 周版 vs 4 周版

### 2 周版（压缩版，风险高）

保留 M0 + M1 + M4 的最小集，**砍掉重要性深度与文件夹比较**：

- M0（2 天）
- M1.1 + M1.2 + M1.4 + M1.5（5 天）——**不换 Myers**（保留 LCS DP，接受内存限制）
- M4.1 + M4.2（3 天）
- 缓冲（2 天）

**产出**：文本比较 CLI + 6 布局报告，45 锚点 status 全绿。
**代价**：不换 Myers → **大文件不可用**（O(n·m) 内存）；无重要性引擎深度；无文件夹比较。

**评价**：可行但**技术债明显**（无非线性内存对齐）。**仅在时间极紧时采用**。

### 4 周版（推荐）

M0 + M1 + M2 + M3 + M4，含缓冲。

**产出**：文本比较（含重要性）+ 文件夹比较（只读）+ CLI + 报告。
**评价**：**这是诚实的 MVP**。四个功能都有黄金数据支撑，验收可量化。

## 5. 每个里程碑的"不达标怎么办"

审计要求"不写假功能"，因此必须预设**失败处理**：

| 情形 | 处理 |
|---|---|
| M2.1 无法验证 U1 | **降级**：MVP 只实现已实测的规则（空白/大小写），**明确标注**"强制重要元素未实现"，不假装 |
| M1.3 Myers 换不动 | **保留 LCS DP 并标注限制**（文件大小上限），不假装支持大文件 |
| M3 criteria 某模式无法对拍 | **只实现已对拍的模式**，报告中列出未支持项 |
| 锚点某些用例始终不一致 | **记录为已知差异**（如已有的 `mixed-side-by-side` 标记省略），写进文档，不隐藏 |
| 时间不足 | **减少功能数，不减少验证**。宁可 3 个功能全绿，不要 6 个功能半绿 |

## 7. MVP 完成的判定标准（可验收）

MVP 宣称完成，须同时满足：

1. `cargo test` 有**真实测试**且全绿（非 0 测试）
2. 文本锚点 **≥80 例**，status 序列对拍 **100%** 一致（已知差异**显式列出**）
3. 文本布局 6 种，**≥29/30** 字节级一致（归一化后）
4. 文件夹夹具 **≥40 例**，`folder-report layout:xml` 对拍一致
5. CLI 脚本子集可跑通，与 BC 产出等价报告
6. **所有未支持的功能在 `--help` 与文档中显式标注**
7. 无"假功能"：任何返回硬编码/占位结果的功能都不算实现

**第 6、7 条是审计纪律的直接体现。**
